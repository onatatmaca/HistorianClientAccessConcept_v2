HistorianSyncTool — Technische Dokumentation

Ein Windows-Forms-Werkzeug zur Synchronisierung zweier GE-Proficy-Historian-Server · .NET Framework 4.8 / C# / x86
Produktionsreif

Dieses Dokument beschreibt den Aufbau der HistorianSyncTool-Anwendung, was jede Datei tut und wie die wichtigsten Benutzerabläufe von Anfang bis Ende funktionieren. Es richtet sich an Entwicklerinnen und Entwickler, die den Code so gut verstehen müssen, dass sie ihn erweitern, debuggen oder erklären können.

Verwenden Sie die Seitenleiste zur Navigation oder drücken Sie Strg+K, um das Inhaltsverzeichnis zu filtern. Für eine druckbare Fassung öffnen Sie Datei → Drucken in Ihrem Browser — das Druck-Stylesheet blendet die Seitenleiste aus, beginnt jeden Hauptabschnitt auf einer neuen Seite und zwingt Diagramme auf volle Seitenbreite.

1. Überblick

1.1 Zweck

HistorianSyncTool ist eine Desktop-Anwendung, die sich mit zwei GE-Proficy-Historian-Servern (einem Primary und einem Secondary) verbindet und vier zusammenhängende Funktionen bietet:

  1. Tags durchsuchen — die auf beiden Servern verfügbaren Tags durchsuchen und Messwerte nebeneinander anzeigen.
  2. Vergleichen — einen Tag zwischen beiden Servern zeitstempelgenau vergleichen und unterschiedliche oder fehlende Werte hervorheben.
  3. Lücken analysieren — historische Daten beider Server über ein wählbares Zeitfenster auf Lücken prüfen und Abdeckung in Balken und einem Detail-Grid visualisieren.
  4. Backfill — fehlende Messwerte von einem Server auf den anderen schreiben, entweder manuell (einmalig) oder nach festem Zeitplan (unbeaufsichtigt).

Die Anwendung ist um ein geschichtetes Design herum aufgebaut, das UI, Services und Datenmodelle trennt und reine Logik-Helfer als testbare Nahtstellen herauslöst. Der Kern der Synchronisation arbeitet mit direktem Zeitstempelvergleich zwischen beiden Servern und erfasst dadurch auch isolierte fehlende Samples unabhängig von der Dauer; jeder Batch-Schreibvorgang ist zudem an eine Read-after-write-Verifikation gekoppelt.

2. Architektur

2.1 Dual-Server-Modell

Die Anwendung arbeitet stets gegen zwei Historian-Instanzen. Sie werden in der API symmetrisch behandelt, haben aber unterschiedliche Rollen in der Praxis:

RolleFeldKonvention
Primary_connections.PrimaryMaßgebliche Datenquelle
Secondary_connections.SecondaryRedundanter / Spiegel-Server

Beide werden in ServerConnection-Objekten verpackt, die dem HistorianConnectionService gehören. Die meisten Operationen benötigen beide Verbindungen. Der Secondary-Hostname wird konventionell vom Primary abgeleitet: Endet der Primary-Hostname auf PC2, wird dieses Suffix beim Secondary entfernt; andernfalls wird PC2 angehängt.

2.2 Geschichteter Aufbau

Der Code ist in vier konzeptuellen Schichten organisiert. Die Abhängigkeitsregel ist einseitig: Forms hängen von Services ab, Services von Models. Services referenzieren niemals WinForms-Steuerelemente — keine Service-Datei enthält using System.Windows.Forms;.

2.4 UI-Thread / Async-Muster

Alle länger laufenden Operationen folgen demselben Muster, um die UI reaktionsfähig zu halten und Wiedereintrittsprobleme zu vermeiden:

Forms/MainForm.cskanonisches Muster
private async void btnSomething_Click(object sender, EventArgs e)
{
    SetBusy(true, "Was ich tue…");      // deaktiviert Aktion-Buttons, zeigt Marquee
    try
    {
        ResetCts();                      // disposed vorherigen CTS, allokiert neu
        var token = _cts.Token;

        // ALLE UI-Werte vorab erfassen, damit der Worker keine Controls berührt
        DateTime from = dtpStart.Value;
        DateTime to   = dtpEnd.Value;
        string   tag  = cboPrimary.Text;

        var result = await Task.Run(() =>
        {
            token.ThrowIfCancellationRequested();
            return _data.ReadRawInRange(_connections.Primary, tag, from, to);
        }, token);

        // Zurück im UI-Thread: Controls direkt aktualisieren
        UpdateGrid(result);
        SetStatus($"{result.Count} Samples gelesen.");
    }
    catch (OperationCanceledException) { SetStatus("Abgebrochen."); }
    catch (Exception ex)                { SetStatus($"Fehlgeschlagen: {ex.Message}", true); }
    finally { SetBusy(false); }
}
Regel Worker-Code innerhalb von Task.Run darf niemals direkt auf Control-Eigenschaften zugreifen. UI-Werte werden vor Task.Run in lokale Variablen kopiert; Updates zurück an die UI laufen über Invoke (Status- und Log-Helfer übernehmen das intern).

Der ResetCts()-Helfer existiert, weil jede länger laufende Operation eine eigene CancellationTokenSource benötigt. Ohne Disposal würden wiederholte Operationen CTS-Instanzen lecken, die finalisierbare Ressourcen halten:

Forms/MainForm.cs
private void ResetCts()
{
    try { _cts?.Dispose(); } catch { }
    _cts = new CancellationTokenSource();
}

4. Formulare (UI)

4.1 MainForm

Datei: Forms/MainForm.cs (~1800 Zeilen) + Forms/MainForm.Designer.cs (Steuerelement-Layout).

Das einzige Top-Level-Form der Anwendung. Hält die Service-Instanzen und koordiniert jede Benutzeraktion. Die Designer-Datei definiert das Layout der Steuerelemente (Statusleiste, linke Seitenleiste mit drei Abschnitten, mittlerer Bereich mit Grids und Buttons, rechtes Panel mit Lückenanalyse). Die andere Datei enthält Event-Handler und Orchestrierung.

Der Kern von ExecuteBackfill (direkter Zeitstempelvergleich)

Dies ist die wichtigste Methode der Anwendung. Sie verwendet keine Lückenfenster — sie liest die Samples beider Server über die volle Auswertungsperiode und kopiert die Zeitstempel, die auf der Quelle vorhanden, aber auf dem Ziel fehlen. So werden auch isolierte fehlende Samples erkannt, die eine intervallbasierte Lückenerkennung übersehen würde.

Schritt 1 — beide Server lesen, den Diff der fehlenden Zeitstempel berechnen und die fehlenden Samples in Schreib-Batches gruppieren:

Forms/MainForm.csExecuteBackfill — Diff & Gruppierung
// Beide Server für die volle Auswertungsperiode lesen
var srcData = _data.ReadRawInRange(sourceConn, tag, evalFrom, evalTo);
var tgtData = _data.ReadRawInRange(targetConn, tag, evalFrom, evalTo);

// Direkter Diff: Zeitstempel auf Quelle, aber nicht auf Ziel
var tgtTicks = new HashSet<long>(tgtData.Select(s => s.Time.Ticks));
var missing = srcData
    .Where(s => !tgtTicks.Contains(s.Time.Ticks))
    .OrderBy(s => s.Time)
    .ToList();

if (missing.Count == 0)
{
    Log($"  {tag}: bereits synchron ({srcData.Count}/{tgtData.Count}).");
    continue;
}

// Fehlende Samples nach Bucket-Dauer gruppieren
var batches = SampleBucketer.GroupByBucket(missing, batchSize);

Schritt 2 — jeden Batch schreiben (unter Erhalt der Qualität pro Sample) und vor der Erfolgszählung mit einem Read-after-write-Check verifizieren:

Forms/MainForm.csExecuteBackfill — Schreiben & Verifikation
foreach (var batchSamples in batches)
{
    var times     = batchSamples.Select(s => s.Time).ToArray();
    var values    = batchSamples.Select(s => s.Value).ToArray();
    var qualities = batchSamples.Select(s =>
        s.Quality >= 100.0 ? DataQuality.Good :
        s.Quality > 0      ? DataQuality.Uncertain :
                             DataQuality.Bad).ToArray();

    var errors = _data.WriteFloatSamplesWithQuality(targetConn, tag, times, values, qualities);
    bool writeOk = errors.Count == 0;

    // Verifikation: Zeitbereich des Batches erneut lesen. ±1 s erweitern, um die
    // Sekunden-genaue Rundung des Historian zu tolerieren (ein Schreiben bei
    // 12:54:30.123 wird als 12:54:30 gespeichert — eine tick-enge Abfrage ab
    // .123 fände nichts).
    bool verifyOk = true;
    if (writeOk)
    {
        DateTime vStart = times[0].AddSeconds(-1);
        DateTime vEnd   = times[times.Length - 1].AddSeconds(1);
        var verify = _data.VerifyWrite(targetConn, tag, vStart, vEnd, times.Length);
        if (verify.Actual < verify.Expected)
        {
            verifyOk = false;
            tagResult.Errors.Add($"Batch {batchIdx}: Verify-Mismatch — " +
                                 $"geschrieben {verify.Expected}, gefunden {verify.Actual}");
        }
    }

    if (writeOk && verifyOk)
    {
        tagResult.BatchesSucceeded++;
        tagResult.SamplesWritten += batchSamples.Count;
    }
    else
    {
        tagResult.BatchesFailed++;
    }
}
Warum direkter Vergleich Ein Backfill nach Lückenfenstern übersieht isolierte fehlende Samples — eine 20-Sekunden-Lücke auf dem Secondary, während der Primary einen Sample hat. Die MinimumGapSeconds-Untergrenze (nötig zur Unterdrückung von Deadband-Rauschen) würde auch echte isolierte Lücken unterdrücken. Der direkte Zeitstempel-Diff hat keine Untergrenze; er kopiert exakt das Fehlende — unabhängig von der Dauer. Eine Referenz-Momentaufnahme der älteren lückenfensterbasierten Implementierung liegt unter _backup/batch-based-backfill-phase6/, falls eine künftige Änderung jemals einen Rollback erfordert.

5.3 GapAnalysisService

Datei: Services/GapAnalysisService.cs

Reine Logik — erkennt Lücken in einer Sample-Zeitliste und plant Per-Batch-Backfill-Fenster. Keine Proficy- oder WinForms-Abhängigkeiten. Der am ausführlichsten getestete Service.

Erkennungsalgorithmus

  1. Deltas zwischen aufeinanderfolgenden Samples berechnen.
  2. ExpectedInterval = Median(deltas) — robust gegen Ausreißer.
  3. threshold = max(median × 1.5, MinGapDuration) — die Untergrenze schützt vor Deadband-Tags.
  4. GapWindow für jedes Paar, bei dem delta > threshold.
  5. Führende + nachlaufende Lücken, wenn Daten das Auswertungsfenster nicht vollständig abdecken.
  6. Leerer Server: eine Lücke über die gesamte Periode emittieren, damit Backfill ein Ziel hat.
  7. Jede Lücke wird in GapBatch-Objekte mit Dauer BatchSize aufgeteilt.
Services/GapAnalysisService.csSchwellwert + leerer Server
result.ExpectedInterval = Median(deltas);

long medianBasedTicks = (long)(result.ExpectedInterval.Ticks * GapThresholdMultiplier);
TimeSpan gapThreshold = TimeSpan.FromTicks(
    Math.Max(medianBasedTicks, _minGapDuration.Ticks));

// Leerer Server: Lücke über ganze Periode emittieren, damit Backfill ein Ziel hat
if (!result.HasData && hasEvalPeriod)
{
    var window = new GapWindow { Start = evalFrom, End = evalTo };
    window.Batches = PlanBatches(window.Start, window.End);
    result.Gaps.Add(window);
    result.CoverageRatio = 0.0;
}

Backfill-Feasibility

Für jeden Batch jeder Lücke werden die Samples des anderen Servers geprüft: Liegt mindestens ein Sample im halboffenen Intervall [batch.Start, batch.End), wird der Batch mit CanBackfill = true markiert. Wird zur farblichen Hervorhebung im Lücken-Grid genutzt; nicht vom Direct-Comparison-Backfill konsultiert.

5.4 RetryHelper

Datei: Services/RetryHelper.cs

Reines Retry-mit-Backoff. Als statischer Helfer herausgelöst, damit es mit injiziertem Sleep-Delegate unit-testbar ist — keine echten Wartezeiten in Tests, keine Proficy-Abhängigkeit.

Services/RetryHelper.cs
public static T Retry<T>(
    Func<T> action,
    int maxAttempts,
    int[] delaysMs = null,
    Action<int> sleep = null)
{
    delaysMs = delaysMs ?? DefaultDelaysMs;     // { 500, 1000, 2000 }
    sleep    = sleep    ?? Thread.Sleep;

    Exception last = null;
    for (int attempt = 0; attempt < maxAttempts; attempt++)
    {
        try { return action(); }
        catch (Exception ex)
        {
            last = ex;
            if (attempt < maxAttempts - 1 && attempt < delaysMs.Length)
                sleep(delaysMs[attempt]);
        }
    }
    throw new InvalidOperationException(
        $"Operation failed after {maxAttempts} attempts: {last?.Message}", last);
}

5.5 SampleFilter

Datei: Services/SampleFilter.cs

Reiner Tupel-Strom-Parser. Verwirft null- und nicht parsbare Werte und beschneidet optional auf das halboffene Intervall [start, end). Der break bei Zeit außerhalb des Bereichs setzt chronologische Eingabe vom Historian voraus.

Services/SampleFilter.cs
public static List<(DateTime Time, float Value, double Quality)> ParseAndClip(
    IEnumerable<(DateTime Time, object Value, double Quality)> raw,
    DateTime start, DateTime end)
{
    var result = new List<(DateTime, float, double)>();
    if (raw == null) return result;
    foreach (var s in raw)
    {
        if (s.Time >= end) break;          // halboffen: end ist AUSSEN
        if (s.Time < start) continue;      // halboffen: start ist INNEN
        if (s.Value == null) continue;
        float v;
        if (!float.TryParse(s.Value.ToString(), out v)) continue;
        result.Add((s.Time, v, s.Quality));
    }
    return result;
}

5.6 SampleBucketer

Datei: Services/SampleBucketer.cs

Gruppiert eine sortierte Sample-Liste in Buckets, in denen jeder Bucket bis zu bucketSize ab der Zeit seines ersten Samples umfasst. Der Bucket-Start setzt sich zurück auf die Zeit des nächsten Samples, sobald der Abstand bucketSize übersteigt.

Services/SampleBucketer.cs
public static List<List<(DateTime, float, double)>> GroupByBucket(
    List<(DateTime Time, float Value, double Quality)> sorted, TimeSpan bucketSize)
{
    var result = new List<List<(DateTime, float, double)>>();
    if (sorted == null || sorted.Count == 0) return result;

    var current = new List<(DateTime, float, double)> { sorted[0] };
    DateTime bucketStart = sorted[0].Time;

    for (int i = 1; i < sorted.Count; i++)
    {
        if (sorted[i].Time - bucketStart < bucketSize)
            current.Add(sorted[i]);
        else
        {
            result.Add(current);
            current     = new List<(DateTime, float, double)> { sorted[i] };
            bucketStart = sorted[i].Time;     // Reset, kein Fortschreiten
        }
    }
    if (current.Count > 0) result.Add(current);
    return result;
}

5.7 ScheduleService

Datei: Services/ScheduleService.cs

Hält einen 15-Sekunden-Polling-System.Windows.Forms.Timer, der ein Delegate auslöst, sobald der Next-Run-Zeitpunkt verstrichen ist. Die eigentliche Arbeit wird delegiert — diese Klasse kümmert sich nur um Taktung, Gating und Next-Run-Buchführung.

Gating-Regeln

Tick-Events werden ignoriert, wenn:

  • der Service deaktiviert ist;
  • bereits ein Lauf in Bearbeitung ist;
  • die aktuelle Zeit vor NextRunUtc liegt.

Next-Run-Berechnung

Services/ScheduleService.cs
private void ComputeNextRun()
{
    var nowUtc = DateTime.UtcNow;

    // Nie gelaufen (oder LastRun uralt) → erster Lauf ein Intervall in die Zukunft.
    if (_lastRunUtc < nowUtc.AddDays(-7))
    {
        _nextRunUtc = nowUtc.AddMinutes(_intervalMinutes);
        return;
    }

    // Nächstes Intervall nach letztem Lauf. Wenn mehrere Intervalle verpasst wurden
    // (Laptop im Standby), kein Nachholbedarf — einfach in 30 s loslegen.
    _nextRunUtc = _lastRunUtc.AddMinutes(_intervalMinutes);
    if (_nextRunUtc < nowUtc) _nextRunUtc = nowUtc.AddSeconds(30);
}

protected override void OnMouseMove(MouseEventArgs e)
{
    int hitIndex = -1;
    for (int i = 0; i < _gapRects.Count; i++)
        if (_gapRects[i].Rect.Contains(e.Location)) { hitIndex = i; break; }

    if (hitIndex == _lastHoverIndex) return;     // Deduplizierung

            $"{seg.Start:yyyy-MM-dd HH:mm} → {seg.End:yyyy-MM-dd HH:mm}\n" +
            $"Dauer: {FormatDuration(seg.End - seg.Start)}",

    else

}

9. Tests

Projekt: HistorianSyncTool.Tests/ — MSTest, .NET 4.8, x86.

Das Test-Projekt referenziert die Proficy-DLL bewusst nicht. Alle vier Testdateien decken reine-Logik-Services ab, die sich mit synthetischen Eingaben prüfen lassen: GapAnalysisService, RetryHelper, SampleFilter, SampleBucketer. Code, der Proficy-Typen anfasst, ist klein gehalten (ein Generator + ein Service-Call-Wrapper), sodass die testbaren Nahtstellen die sinnvolle Logik abdecken.

Test-KlasseAbdeckungFälle

RetryHelperTests Erfolg / Fehler / Backoff-Timing 8 — Erfolg-ohne-Sleep, Fehler-dann-Erfolg-mit-einem-Sleep, alle-Fehler-wrapped, kein-Sleep-nach-letztem-Versuch, kürzere Delay-Arrays toleriert, Argument-Validierung.

10. Build & Auslieferung

  • OS: Windows (x86-kompatibel).
  • .NET Framework: 4.8 (Developer-Pack zum Kompilieren, Runtime zum Ausführen).

  1. HistorianSyncTool.sln öffnen.
  2. Solution-Konfiguration → Release.
  3. Plattform → x86.
  4. Build → Projektmappe neu erstellen (Strg+Alt+F7).

$msb = "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\MSBuild\Current\Bin\MSBuild.exe"

11. Glossar

BegriffDefinition
BackfillDas Schreiben fehlender Messwerte von einem Server zum anderen.
BatchEin Bucket von Samples (Standard 10 min), der in einem einzelnen IData.Add-Aufruf geschrieben und individuell verifiziert wird.
ClientAccess-APIDie .NET-Assembly Proficy.Historian.ClientAccess.API.dll mit ServerConnection, IData, ITags etc.
CoverageRatio (Abdeckung)(GesamtSpanne − FehlendeDauer) / GesamtSpanne — 0,0 bis 1,0.
DeadbandEine Historian-Collector-Einstellung, die nur dann einen Sample schreibt, wenn sich der Wert um mehr als einen Schwellwert ändert. Erzeugt unregelmäßige Intervalle.
Direct ComparisonAktuelle Backfill-Strategie: Zeitstempel kopieren, die auf der Quelle vorhanden, aber auf dem Ziel fehlen — ohne Lückenfenster-Heuristik.
AuswertungsfensterDer vom Benutzer gewählte [from, to]-Bereich, der Analyse und Backfill begrenzt.
Untergrenze (MinimumGapSeconds)Absolutes Minimum, das ein Delta überschreiten muss, um als Lücke markiert zu werden. Standard 120 s.
Lückenfenster (GapWindow)Ein [start, end]-Intervall ohne Samples. Wird von GapAnalysisService.PlanBatches in Batches geteilt.
Halboffenes Intervall[start, end) — start inklusiv, end exklusiv.
HistSyncKonfigurierbarer "Heartbeat"-Tag, der als Fallback dient, wenn kein Tag ausgewählt ist. Standardname "HistSync".
Median-IntervallMedian aller aufeinanderfolgenden Sample-Deltas — robust gegen Ausreißer. Treibt den Schwellwert.
net.tcpDas WCF-Binding, das die Proficy-ClientAccess-API verwendet. Standard-Port 13000.
Primary / SecondaryDie beiden Historian-Server. Primary ist maßgeblich; Secondary spiegelt.
QualityPer-Sample-Zuverlässigkeitsflag: Good / Uncertain / Bad. Wird beim Backfill erhalten.
Tick100-Nanosekunden-Einheit von .NET-DateTime. Der Direct-Comparison-Diff hasht über Time.Ticks (long) für schnellen Set-Lookup.
Unattended (unbeaufsichtigt)Geplanter Modus — unterdrückt SyncReportDialog und loggt in Datei.
Verify (read-after-write)Nach jedem Schreiben wird [firstTime − 1 s, lastTime + 1 s] erneut gelesen und actual ≥ expected geprüft. Die ±1 s tolerieren die Sekunden-genaue Rundung des Historian.
